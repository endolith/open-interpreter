# Code Evaluation

Code evaluation asks a **decision model** what a code block would do, then prints a
one-line verdict beside the approval prompt:

```
  Safety: GREEN  impact 0.4/4  (jev-1.13.0, 312 ms)
  Safety: RED    impact 3.9/4  destroys data 0.91 · buggy 0.62  (jev-1.13.0, 340 ms)
```

It is **display-only**. It does not block execution, does not approve it, and does
not replace the confirmation prompt. It is meant to make a block's likely effects
visible before you say yes.

## Enabling it

```shell
interpreter --code_evaluation
```

```yaml
# ~/.config/open-interpreter/profiles/default.yaml
code_evaluation: true
```

## Choosing a model

The default is TypeSafe's Jev (`typesafe/jev-latest`), which needs
`TYPESAFE_API_KEY`. Any decision model supported by LiteLLM works, because the
request is the same typed-question format regardless of provider:

```shell
# OpenAI
interpreter --code_evaluation --code_evaluation_model openai/gpt-6-luna

# Cloudflare (open weights, also self-hostable)
interpreter --code_evaluation --code_evaluation_model cloudflare/clef-flash

# Through OpenRouter
interpreter --code_evaluation --code_evaluation_model openrouter/typesafe/jev-1.14
```

### OpenRouter

OpenRouter serves decision models on its own decisions endpoint; LiteLLM routes
`openrouter/…` ids there automatically (it calls `/api/alpha/decisions`, not chat
completions). Set `OPENROUTER_API_KEY` and prefix the OpenRouter id with
`openrouter/`:

```yaml
code_evaluation: true
decision_model:
  model: openrouter/typesafe/jev-1.14
```

Ids seen on OpenRouter include `typesafe/jev-1.14`, `openai/gpt-6-luna-decisions`,
`cloudflare/clef-flash`, `cloudflare/clef`, `perplexity/pplx-decider-v1.2`, and
`liquid/d1` — prefix each with `openrouter/` (for example
`openrouter/cloudflare/clef-flash`). Availability changes, so use the id as
OpenRouter lists it. `OPENROUTER_API_BASE` overrides the default
`https://openrouter.ai/api`.

If the line reads `UNKNOWN` with `404: No endpoints found …`, the provider's
privacy settings excluded the model; Open Interpreter is fine. Check
[OpenRouter privacy](https://openrouter.ai/settings/privacy): “ZDR endpoints only”
requires the model to have a zero-retention endpoint (try `typesafe/jev-1.13`), and a
training policy can exclude others. `401` means a missing or wrong
`OPENROUTER_API_KEY`. LiteLLM 1.105.x builds the decision request body itself and
does not forward a per-request `provider` block, so put ZDR at the account level
rather than in the request.

For open weights, use `cloudflare/clef-flash` (Apache-2.0, 9B) or self-host Clef,
Liquid d1, Strands Decider, or Kev. None of the decision models is code-specific;
they judge effects, which is the point — they are not a CVE scanner. Clef and
Clef Flash cap the text state at 2,000 UTF-8 bytes *including the policy*, so
lower `decision_model.max_chars` (roughly 1,000) and keep the policy short there.

For a local server that speaks the System One API (vLLM, Laya, Strands Decider,
EdgeJev, …), point `--code_evaluation_api_base` at it:

```shell
interpreter --code_evaluation \
  --code_evaluation_model hosted_vllm/Qwen/Qwen3-0.6B \
  --code_evaluation_api_base http://localhost:8000
```

## What it asks

Rather than one "is this safe?" question, the evaluator asks several atomic ones
and combines the answers in code, so a verdict is explainable:

| Question | Meaning |
|---|---|
| `destroys_data` | deletes, overwrites, truncates, or irreversibly loses data |
| `exposes_secrets` | prints/logs/returns credentials or secrets in output |
| `sends_data_out` | sends data to a network service, or encodes it for later |
| `modifies_system` | changes state beyond the project (OS, packages, services, permissions) |
| `execution` | none / visible / untrusted code (untrusted = fetched from the network or decoded, so what runs is not in the block) |
| `resource_exhaustion` | unbounded CPU, memory, disk, or processes |
| `buggy` | likely to fail or behave differently from what it appears to do |
| `impact` | score from 0 (no lasting effect) to 4 (irreversible/catastrophic) |

A flag fires at probability **0.6**. Any red flag (`destroys_data`,
`exposes_secrets`, `sends_data_out`, `runs_untrusted_code`) makes the block red; any
yellow flag makes it yellow; otherwise it is green. `buggy` is a yellow flag. If the
model cannot answer (timeout, missing key, refusal), the line says `UNKNOWN` and
never `GREEN`.

Running a shell or a project script whose behavior the block shows is yellow;
running code the block cannot show is red. `echo 'echo hi' | bash` is yellow, but
`curl … | bash`, `base64 -d … | sh`, or `eval` of a remote string is red — the
reviewer cannot tell what will execute, which is exactly the compromised-assistant
case.

The state sent to the model is the code block, its language, the tracked working
directory, and the policy text. Python kernel state is **not** sent. You can replace
the policy with `--code_evaluation_policy`.

## Secrets

The snippet is passed through the same secret detector as the chat path
(`sanitize_secrets`), so literal keys, tokens, and passwords are replaced with
`[REDACTED]` before leaving the machine when that setting is `auto` or `on`. This is
defense in depth, not anonymity: the code itself still goes to the decision-model
provider unless you run a local model.

## Cost and latency

A decision-model call takes roughly 0.1–0.5 seconds and is priced per input token
(typically a fraction of a cent per block). The evaluation happens after the code
block has finished streaming and before the approval prompt, so it is normally
hidden by the time you read the block. Results are cached per session: an identical
block is only sent once.

## Not a security boundary

A decision model can be wrong, and `jev-latest` can change under you. Treat the
line as a second opinion, not a guarantee, and validate the thresholds on your own
labelled blocks before letting anything act on the verdict. A future allowlist rule
may be able to authorize blocks the model calls safe; the `would_allow` field is
already computed for that, but nothing consumes it yet.
